## 1. 개요 (Overview)

AI 에이전트(Claude Code 등)와 함께 진행하는 개발 작업을 **로컬에서 관리하는 이슈 트래커**다.
기존에 Jira로 하던 백로그·스프린트 운영을 로컬로 옮기되, 단순 이관이 아니라
**사람과 AI 에이전트가 같은 보드를 함께 읽고 쓰는 장(場)** 으로 재설계한다.

핵심 성질 네 가지:

1. **파일이 원본(SoT), SQLite는 인덱스** — 이슈 1건 = 마크다운 파일 1개. git으로 히스토리·diff·리뷰가 되고 AI가 파일을 직접 읽어도 된다. SQLite는 조회·집계용 파생 캐시이며 삭제 후 재생성해도 데이터 손실이 없다.
2. **쓰기는 단일 writer** — `.localjira/`에 대한 도메인 쓰기는 로컬 API 서버 프로세스만 수행한다. 사람·CLI·에이전트 모두 같은 REST API를 거친다. 에디터 직접 편집은 허용하되 `external` 변경으로 조정(reconcile)한다.
3. **에이전트가 1급 사용자** — 토큰 + scope로 인증되며, 작업을 **선점(claim)** 하고 실행 로그를 보고한다. "누가 바꿨는지"는 항상 구분되어 표시된다.
4. **로컬 우선** — 외부 SaaS 이슈 트래커에 의존하지 않고 기동한다. 네트워크를 쓰는 곳은 **팀 공유용 git 원격 동기화**와 **선택적 LLM 호출** 둘뿐이며, 둘 다 없어도 단독 사용이 가능하다.

1차 범위는 **백로그 관리 + 스프린트 관리**로 한정한다.

## 2. 배경 및 문제 정의 (Background & Problem)

| # | 현재 문제 | 근거 |
|---|---|---|
| P1 | 작업의 실제 수행 주체가 AI 에이전트로 옮겨갔는데, Jira 워크플로는 사람이 수동으로 티켓을 옮기는 것을 전제한다. 상태가 항상 실제보다 뒤처진다. | 세션 종료 후 티켓 갱신 누락 |
| P2 | AI 세션·브랜치·커밋과 티켓이 끊겨 있다. "이 이슈를 어떤 세션이 어디까지 했나"가 추적되지 않는다. | 커밋 메시지에만 흔적이 남음 |
| P3 | 티켓 내용을 AI에게 넘기려면 사람이 복사·붙여넣기 해야 한다. 컨텍스트 전달 비용이 크다. | Jira REST 연동은 무겁고 네트워크·권한 필요 |
| P4 | 여러 에이전트를 동시에 돌리면 **같은 작업을 중복 수행**하거나, 죽은 세션이 이슈를 점유한 채 남는다. 이를 막을 장치가 지금 없다. | 병렬 워크트리 운용 시 실제 발생 |
| P5 | 티켓 데이터가 SaaS에 갇혀 코드와 함께 버전 관리되지 않는다. 코드 리뷰 시 요구사항 변경 이력을 같이 볼 수 없다. | — |

→ **로컬에서 돌고, 파일 기반이라 git에 얹히며, 에이전트가 안전하게 선점·보고할 수 있는 백로그·스프린트 도구**가 필요하다.

## 3. 목표 / 비목표 (Goals / Non-Goals)

- **목표**
  - **G1 백로그** 이슈 CRUD, 계층(에픽→스토리→서브태스크), 관계(blocked_by 등), 순서 정렬, 필터·검색.
  - **G2 스프린트** 생성·시작·종료, 스코프 확정, 칸반 보드. *(번다운·완료율 분석은 P1 후속)*
  - **G3 사람–AI 공동 운영** 에이전트 토큰·scope, 작업 선점(claim/lease), 실행 로그(세션·브랜치·커밋) 연계, 사람의 개입·회수 수단.
  - **G4 저장 신뢰성** 파일 SoT + SQLite 인덱스. **인덱스 유실·프로세스 크래시** 후에도 도메인 데이터(이슈·코멘트·스프린트·run·이벤트)는 파일만으로 100% 복구. *(claim/lease는 런타임 상태라 복구 대상이 아니고, 디스크 장애는 보장 범위 밖 — D5)*
  - **G5 팀 사용** 로컬 계정 로그인·역할·scope 권한, git으로 데이터 동기화.
- **비목표** (1차 범위 밖)
  - 워크플로 커스터마이징(상태 전이 규칙 편집 UI), 커스텀 필드 정의.
  - 로드맵/간트, 릴리스 관리, 워크로그(시간 기록)·타임시트.
  - 실시간 다중 편집(CRDT), 외부 SSO/OIDC, 서버 호스팅·멀티 테넌시.
  - **Jira 데이터 임포트 일체**(양방향 동기화는 물론 단방향 CSV 임포트도 제외 — D6). 알림 발송(1차는 In-App 활동 피드까지).
  - **변조 방지(tamper-evident) 감사** — §5.7 참조. 1차 이벤트 로그는 "협업 이력"이지 보안 감사 증적이 아니다.

## 4. 사용자 및 시나리오 (Users & Scenarios)

| 역할 | 설명 | 주 사용 화면 |
|---|---|---|
| **오너/PO** | 백로그 정제·우선순위·스프린트 계획 | 백로그, 스프린트 계획 |
| **개발자** | 스프린트 내 작업 수행·상태 갱신, 에이전트 감독 | 보드, 이슈 상세 |
| **AI 에이전트** | 토큰 인증 머신 계정. 작업 선점·상태 전이·코멘트·실행 로그 보고 | REST API (UI 없음) |

핵심 시나리오:

- **S1 (백로그 적재)** PO가 에이전트에게 요구사항을 주고 적재를 지시 → 에이전트가 자기 토큰으로 `POST /issues`를 호출해 이슈를 `BACKLOG`로 만든다 → 사람이 검토하고 쓸 것만 `TODO`로 올린다. **제품이 LLM을 호출하지 않는다**(D16). 검토 장치는 셋이다: 미커밋 파일(D4·R25), `BACKLOG`는 claim 불가(§6.1), 그리고 `created_by_kind=agent` 배지(§8).
- **S2 (스프린트 계획)** 백로그 상위 항목을 스프린트에 담고 포인트 합계·용량을 보며 확정 → 시작.
- **S3 (에이전트 작업)** 에이전트가 `GET /issues?sprint=active&status=TODO&claimable=true`로 후보를 받아 `POST /issues/{id}/claim`으로 **원자적 선점** → `IN_PROGRESS` 전환, AgentRun 시작, 브랜치·세션 연결 → 주기적 heartbeat → 완료 시 구조화된 결과 제출 + `IN_REVIEW` 전환.
- **S4 (사람 개입)** 사람이 보드에서 에이전트 진행 카드를 본다. 이견이 있으면 **claim 해제·run 취소**로 회수하고, 취소된 run의 후속 쓰기는 거부된다.
- **S5 (에이전트 중단)** 에이전트가 죽어 heartbeat가 끊기면 lease 만료 → run `STALE` 표시 → 사람이 회수·재할당한다. 이슈가 영구 점유되지 않는다.
- **S6 (팀 동기화)** 팀원이 `git pull` → 파일 변경 조정(reconcile) → 보드에 반영. 충돌·중복 키가 있으면 해당 항목만 격리 표시된다.

## 5. 도메인 모델 · 저장 구조

### 5.1 엔티티

| 엔티티 | 설명 | 주요 필드 |
|---|---|---|
| `Project` | 이슈 키 접두사 단위 | key(LJ), name, timezone, estimation_unit(= 스토리 포인트 고정, D8) |
| `Issue` | 백로그의 기본 단위 | uid(ULID), key(LJ-12), former_keys[], type, title, status, parent, sprint, assignee, points, backlog_rank, board_rank, labels, links[], created_by_kind, content_hash |
| `IssueLink` | 이슈 간 관계 | from, to, kind(`blocks`/`blocked_by`/`relates_to`/`duplicates`) |
| `Sprint` | 기간이 있는 작업 묶음 | id, name, goal, start_at, end_at, status, capacity |
| `Comment` | 대화(사람·에이전트 공용). 원문 불변 + 후속 op로 상태 변경 | comment_id(ULID), author_id, author_display_name, actor_kind, kind, body, created_at |
| `CommentOp` | 코멘트에 대한 후속 조작 | comment_id, op(`resolve`/`unresolve`/`edit`/`delete`), actor, at, payload |
| `Claim` | 작업 선점권. **런타임 상태**(파일 SoT 아님, §5.4) | issue, owner_id, run_id, acquired_at, lease_expires_at |
| `AgentRun` | AI 작업 실행 로그 | run_id, agent_id, initiated_by, issue, session_id, branch, commits[], started_at, last_heartbeat_at, ended_at, state, result |
| ~~`Proposal`~~ | **철회(D16).** AI 정제를 제품 기능으로 만들지 않으므로 이 엔티티는 존재하지 않는다 | — |
| `User` | 로컬 계정 / 머신 계정 | id, display_name, role(`admin/member/agent`) |
| `Token` | PAT | token_id, user, scopes[], project_scope, expires_at, last_used_at |
| `Event` | 변경 이력(append-only) | event_id, at, actor_id, actor_kind(`human/agent/external/system`), run_id, target, verb, before/after |

- **이슈 타입**: `epic | story | task | bug | spike | subtask`.
  계층 규칙 — `epic`은 최상위(부모 불가). `story/task/bug/spike`는 `epic`만 부모로 가진다.
  `subtask`는 `epic`을 제외한 작업형 이슈만 부모로 가지며 **자식을 가질 수 없다**. 순환 금지.
- **부모 삭제 정책**: 하위 이슈가 있으면 기본은 **삭제 차단(409)** 이다. `strategy` 파라미터로만 진행한다 —
  `promote`(하위를 부모 없는 최상위로 승격) 또는 `cascade_cancel`(하위를 `CANCELLED`로 전환 후 부모 삭제). 하위를 조용히 고아로 만들지 않는다.
- **assignee**는 human·agent User 모두 가능하다. **assignee는 계획상 책임자, claim owner는 현재 실행 주체**이며 서로 독립이다.
- **정렬 필드는 2개**다. `backlog_rank`(프로젝트 백로그 순서)와 `board_rank`(정렬 영역 = `(sprint_id, status)`). 스프린트에서 빠져도 `backlog_rank`는 보존한다.
- **`created_by_kind`는 불변**, 카드 배지는 **마지막 도메인 변경의 actor_kind**를 표시한다(§7).

### 5.2 상태 전이 (명시적 정의)

이슈 상태 — 1차에서는 아래 표가 고정이며 편집 불가다.

| From \ To | BACKLOG | TODO | IN_PROGRESS | IN_REVIEW | DONE | BLOCKED | CANCELLED |
|---|---|---|---|---|---|---|---|
| **BACKLOG** | — | ✅ | — | — | — | ✅ | ✅ |
| **TODO** | ✅ | — | ✅ | — | — | ✅ | ✅ |
| **IN_PROGRESS** | — | ✅ | — | ✅ | — | ✅ | ✅ |
| **IN_REVIEW** | — | — | ✅ | — | ✅ | ✅ | ✅ |
| **DONE** | — | — | ✅ | — | — | — | — |
| **BLOCKED** | `blocked_from`으로만 복귀 (진입 시 이전 상태 보존) | | | | | — | ✅ |
| **CANCELLED** | ✅ (`admin`만) | — | — | — | — | — | — |

- 스프린트 상태: `PLANNED → ACTIVE → CLOSED`. **동시 ACTIVE는 프로젝트당 1개.** 전이는 **명시적 명령으로만** 발생하며 날짜 경과로 자동 전이하지 않는다.
- `start_at`/`end_at`은 프로젝트 timezone이 포함된 RFC 3339 timestamp다. **저장되는 모든 시각은 RFC 3339**로 통일하고, 사람이 읽는 형식은 렌더링 시점에 만든다.
- 미완료 `blocked_by`가 있는 이슈는 `claimable=false`이며, API가 그 사유를 함께 반환한다.

### 5.3 파일 레이아웃 (SoT)

```
.localjira/
  config.yaml                          # 프로젝트·용량·timezone·schema_version
  users.yaml                           # 계정 식별자·표시명·역할만 (자격증명 없음)
  projects/LJ.yaml
  issues/LJ/LJ-12.md                   # 이슈 1건 = 파일 1개 (frontmatter + 본문)
  comments/LJ-12/01J8XR....md          # 코멘트 원문 = 불변 파일 (ULID = 시간순)
  comments/LJ-12/01J8XR....ops.jsonl   #   ↳ 해당 코멘트의 후속 op (resolve/edit/delete)
  sprints/LJ/LJ-S3.yaml
  runs/LJ/2026-07/01J8XS....json
  # proposals/ 는 만들지 않는다 — D16으로 철회. 코드에 남은 경로 인식은 무해한 사문(死文)이다
  events/2026-07-27/<node_id>.jsonl    # 클론(설치)별 분리 — 파일당 writer 1개 보장
  .local/                              # ★ .gitignore — 재생성 가능/기기 고유
    index.sqlite                       #   파생 인덱스
    credentials.sqlite                 #   비밀번호·토큰 해시 (git 추적 금지)
    outbox.sqlite                      #   쓰기 저널 + 멱등성 키 (§5.5)
    runtime.sqlite                     #   claim/lease 등 런타임 상태 (§5.4)
```

**분할 근거** — 코멘트·이벤트를 이슈 파일이나 날짜별 단일 파일에 append하면, 두 클론이 같은 파일의 같은 위치를 수정해 **머지 충돌이 상시 발생**한다. 코멘트는 1건 = 1파일, 이벤트는 `node_id`(설치 시 발급되는 ULID)별 파일로 쪼갠다. 한 프로세스만 쓰기 때문에 파일 내 append는 안전하고, 서로 다른 클론끼리는 파일이 달라 충돌하지 않는다.

**브랜치 배치 (D1 — 하나의 공유 보드)**

`.localjira/`는 코드 브랜치를 따라가지 않는다. 같은 저장소의 **orphan 브랜치 `localjira/data`** 를 리포 루트에 worktree로 붙인다.

```bash
git switch --orphan localjira/data && git commit --allow-empty -m "init board" && git switch -
git worktree add .localjira localjira/data
echo ".localjira/" >> .gitignore          # 코드 브랜치에서는 무시
```

- 코드 브랜치를 오가거나 `.worktree/*`를 여러 개 써도 **보드 상태는 항상 하나**다. 스프린트 ACTIVE 유일성·claim·ETag가 브랜치마다 갈리지 않는다.
- 보드 데이터 커밋이 코드 히스토리에 섞이지 않고, 반대로 코드 리뷰에도 잡히지 않는다.
- **서버는 리포 루트의 `.localjira/` 한 곳만 잡는다.** 다른 워크트리에서 작업하는 사람·에이전트는 파일이 아니라 서버 URL로 접근하므로 단일 writer 원칙(§5.4)이 자연히 지켜진다.
- 동기화는 `git -C .localjira pull --rebase` / `push` (D2). 상시 공유 서버는 두지 않는다.

이슈 파일 형식:

```markdown
---
uid: 01J8XQ9F3M2K7B4N5P6Q7R8S9T     # 불변 내부 식별자 (ULID)
key: LJ-12                           # 표시용 키 (충돌 시 자동 재발급, D3)
```

### 5.4 쓰기 경로 · 동시성

- **단일 writer 원칙**: 도메인 쓰기는 로컬 API 서버 프로세스만 한다. CLI·에이전트·웹 UI 모두 HTTP를 거친다. 서버는 기동 시 lock 파일을 잡아 **동일 `.localjira`에 대한 두 번째 서버 기동을 거부**한다.
- **원자적 저장**: 대상과 **같은 디렉터리**에 temp 파일 생성 → 내용 flush + `fsync` → `rename` → **부모 디렉터리 `fsync`**. 동일 파일 쓰기는 프로세스 내 mutex로 직렬화한다.
- **낙관적 동시성**: 조회 응답은 **API 표현(JSON) 바이트의 강한 ETag**(`ETag: "<sha256 hex 64자>"`)를 반환하고, 변경 요청은 이를 `If-Match`로 보낸다(D15).
  - `If-Match` **누락은 428 Precondition Required**, 불일치는 **412 Precondition Failed**다. 누락과 불일치는 클라이언트가 할 일이 다르므로 상태코드를 구분한다.
  - 412 응답에는 **현재 문서 전문 + 최신 ETag + 거부된 요청 값**을 담는다. 서버는 클라이언트의 base 스냅샷을 보관하지 않으므로 3-way diff는 클라이언트가 자기 base로 계산한다.
  - ETag는 **파일 바이트가 아니라 API가 실제로 전송하는 표현**에 붙는다. 파일 바이트 해시(`file_hash`)는 워처·조정용으로 따로 두며 서로 대신 쓰지 않는다.
  *(정수 `rev`는 분산 환경에서 서로 다른 클론이 같은 다음 값을 만들어내므로 동시성 토큰으로 쓰지 않는다. 표시·이력용으로만 둔다.)*
- **멱등성**: 모든 생성·append API(`POST /issues`, `/comments`, `/runs`)는 `Idempotency-Key`를 지원한다. `(actor_id, key)` → 최초 응답을 `.local/outbox.sqlite`에 **24시간 보존**(재기동 후에도 유효)하며, 재요청은 최초 결과를 그대로 반환하고 중복 생성·중복 이벤트를 만들지 않는다. 만료된 키의 재요청은 새 요청으로 처리된다.
- **런타임 상태 분리**: `Claim`/lease는 클론 간에 공유해도 의미가 없고 오히려 유령 점유를 만든다. 따라서 파일 SoT가 아니라 `.local/runtime.sqlite`에 저장하며, **서버 재기동 시 만료된 claim은 전량 회수**된다. 다만 claim 취득·해제·강제 회수 **사실**은 이벤트로 파일에 남아 이력은 보존된다.
- **식별자 발급**: 내부 `uid`는 ULID(충돌 없음), 표시 키 `LJ-12`는 서버가 발급한다. 서로 다른 클론이 같은 키를 만들어 머지된 경우 **uid는 그대로 두고 표시 키만 자동 재발급**한다(D3) — `uid` 생성 시각이 나중인 쪽이 새 키를 받고, 이전 키는 `former_keys[]`에 남아 조회·링크·검색이 계속 동작한다.

### 5.5 파일 ↔ 인덱스 동기화

| 상황 | 동작 |
|---|---|
| **API 쓰기** | ① `outbox`에 변경 레코드 기록 → ② 파일 원자적 교체 → ③ 인덱스 upsert → ④ 이벤트 append → ⑤ outbox 완료 표시. ③~④는 멱등이며, 기동 시 미완료 outbox를 재생(replay)한다. |
| **자기 쓰기 되울림** | writer가 남긴 `write_op_id`+최종 content hash를 워처가 다시 관측하면 재파싱은 하되 **추가 도메인 변경·이벤트를 만들지 않는다**. |
| **외부 파일 변경** | 워처 이벤트는 **힌트로만** 쓴다. debounce(≥300ms) 후 영향 디렉터리를 재스캔한다. |
| **git checkout/pull, 대량 변경, 이벤트 overflow** | `.git/HEAD`·`index` 변화 또는 임계치 초과를 감지하면 **전체 조정(reconciliation)** 을 수행한다. |
| **기동 시** | 저장된 `(path, file identity, mtime, size)`로 후보를 좁히고 **후보만 hash 검증**한다. 명시적 "전체 검증"은 모든 파일 hash를 재계산한다. |
| **파일 삭제·rename** | debounce·조정 후 인덱스에 **tombstone**으로 반영한다. 동일 uid의 rename은 이동으로 인식하고, 유예기간(기본 60s) 내 재등장하면 동일 엔티티로 복원한다. |
| **인덱스 손상·스키마 변경** | `.local/index.sqlite` 삭제 후 전체 재빌드 (데이터 손실 0). |

### 5.6 무결성 검증 · 격리

파싱에 성공해도 도메인 불변조건이 깨질 수 있다(머지가 만들어내는 상황). **파싱과 도메인 검증을 분리**한다.

| 검출 대상 | 조치 |
|---|---|
| YAML/frontmatter 파싱 실패 | 기존 인덱스 레코드를 `INVALID`로 격리. 일반 조회·집계에서 제외하되 **삭제하지 않는다**. 마지막 정상 hash·오류·발견 시각을 오류 테이블에 보존 |
| git conflict marker(`<<<<<<<`) 포함 | 위와 동일 격리. 인덱싱하지 않는다 |
| 중복 표시 키 | **자동 재키잉**(D3) — `uid` 생성 시각이 나중인 쪽에 새 키 발급, 이전 키는 `former_keys[]`로 보존. 격리하지 않고 정상 동작시킨다 |
| 중복 `uid` | 자동 해결 불가(어느 쪽이 원본인지 알 수 없다). 양쪽 격리 후 사람이 해결 |
| 존재하지 않는 parent·sprint 참조, 계층 순환 | 해당 엔티티 격리 + 수정 후보 표시 |
| ACTIVE 스프린트 2개 이상 | 프로젝트 전체를 "스프린트 충돌" 상태로 표시하고 시작/종료 명령 차단 |
| 중복 `rank` | 오류가 아니라 `(rank, uid)` 결정적 tie-break로 정렬. 재균형 대상으로 표시 |

- 오류 배너는 **영향받는 프로젝트의 모든 화면 + 설정 화면**에 표시하며 파일 경로·오류·복구 방법을 보여준다.
- **격리된 엔티티와 이를 직접 참조하는 관계의 변경은 복구 전까지 차단**하고, 나머지는 정상 동작한다.

### 5.7 순서(rank)와 감사 로그에 대한 정직한 한계

- **LexoRank**는 일반 이동 시 **이동 대상 1개 파일만** 바꾸므로 정수 position보다 충돌이 훨씬 적다. 다만 인접 rank 사이 공간이 소진되면 **구간 재균형으로 여러 파일이 함께 변경**되고, 서로 다른 브랜치가 같은 간격에 삽입하면 **동일 rank가 생길 수 있다**. 따라서 정렬은 항상 `(rank, uid)`로 결정적이어야 하며, 재균형 정책과 중복 감지가 필요하다. *("충돌이 나지 않는다"는 주장은 사실이 아니다.)*
- **이벤트 로그는 협업 이력이지 변조 방지 감사 증적이 아니다.** 파일 SoT 구조에서는 누구나 이벤트 파일을 편집·삭제할 수 있다. 변조 탐지가 필요해지면 hash chain 또는 서명을 별도 요구사항으로 추가한다(현재 비목표).
- **API 밖에서 발생한 파일 변경은 주체를 신뢰성 있게 식별할 수 없다.** `actor_kind=external`, `actor_id=unknown`으로 기록하고, git commit author를 찾을 수 있어도 `source_commit` 참고 정보로만 남기며 인증된 actor로 간주하지 않는다.

## 6. 사람–AI 협업 규약

이 절이 이 제품이 일반 로컬 칸반과 갈리는 지점이다.

### 6.1 작업 선점 (claim / lease)

- 에이전트는 상태를 직접 바꾸기 전에 `POST /issues/{id}/claim`으로 **원자적으로 선점**한다. 유효한 claim이 이미 있으면 **409**를 반환한다. *(조회 후 상태 변경만으로는 두 에이전트의 동시 진입을 막지 못한다.)*
- **claim 대상은 `TODO` 상태의 이슈**다(중단된 자기 작업 재개 시 `IN_PROGRESS`도 허용). `BACKLOG` 항목은 사람이 `TODO`로 올린 것만 에이전트가 집는다 — 정제되지 않은 백로그를 에이전트가 임의로 착수하지 않게 하기 위한 제약이다. **D16 이후 이 제약이 AI 산출물의 주 검토 관문이다**: 에이전트가 백로그를 적재하더라도 사람이 `TODO`로 올리기 전에는 자기가 만든 것을 자기가 착수할 수 없다. 거부 코드가 `E_CLAIM_NOT_REFINED`인 것이 그 뜻이다.
- **claim과 전이의 강제 결합**: `actor_kind=agent`가 `IN_PROGRESS`·`IN_REVIEW`·`DONE`으로 전이하려면 **본인이 보유한 유효 claim이 필수**이며, 없으면 `issue:transition` scope가 있어도 **403**이다. 사람은 claim 없이 전이할 수 있으나, 타인의 유효 claim이 있으면 경고와 함께 강제 여부를 확인받는다.
- claim에는 `owner_id`, `run_id`, `lease_expires_at`이 기록된다. **heartbeat(60초 주기)는 성공할 때마다 `lease_expires_at`을 15분 뒤로 갱신**한다.
- **`STALE`과 lease 만료는 다른 것이다**(D10). 셋을 구분한다.

  | 단계 | 시점 | 의미 | claim 유효? |
  |---|---|---|---|
  | 정상 | heartbeat 수신 중 | 진행 중 | ✅ |
  | **`STALE` 표시** | 마지막 heartbeat +3분(3회 연속 누락) | "응답 없음" **경고 표시일 뿐** — 사람에게 이상을 알리는 UI 신호 | ✅ (아직 유효) |
  | **lease 만료** | 마지막 heartbeat +15분 | 점유권 소멸. 다른 에이전트가 claim 가능 | ❌ |

  3분에 곧바로 회수하지 않는 이유: 긴 빌드·테스트 중 heartbeat가 잠시 밀리는 것과 프로세스가 죽은 것을 구분해야 하기 때문이다. 사람은 `STALE`을 보고 **기다릴지 강제 해제할지 판단**한다.
- **사람은 lease 만료 전이라도 언제든 claim을 강제 해제**할 수 있다(`member` 이상, 사람 우선권).
- **회수·해제 시 이슈 상태는 자동으로 되돌리지 않는다**(D10). `IN_PROGRESS`인 채로 claim만 풀린다. 되돌리면 에이전트가 중간까지 해둔 작업의 흔적이 사라지고, "자기 작업 재개" 경로(§6.1 2번째 항목)도 막힌다. 사람이 필요하다고 판단하면 명시적으로 `TODO`로 내린다.
- **동일 owner의 재claim은 멱등**이다 — 200과 함께 lease만 갱신한다(409 아님). 네트워크 재시도로 자기 claim을 잃지 않게 한다.
- claim 해제·run 취소 후 해당 run의 쓰기 요청은 **409**로 거부하며, 취소 사유·수행자를 이벤트로 남긴다.

### 6.2 실행 로그 (AgentRun)

- 시작 시 `session_id`, `agent_id`, `initiated_by`(지시한 사람 계정), `branch`를 등록한다. **대리 실행이면 UI와 이벤트에 실행 주체와 지시 주체를 모두 표시**한다.
- 종료 시 **구조화된 결과**를 제출한다: 결과 요약, 검증 방법·통과 여부, 변경 파일, 커밋 해시, 잔여 위험.
- 작업 조회 API는 에이전트에게 **구조화된 컨텍스트**를 반환한다: 현재 ETag, 목표, 인수조건, 의존성, **최신 사람 지시**, 허용 작업 범위. 코멘트 전문을 통째로 읽고 알아서 판단하게 두지 않는다.

### 6.3 코멘트 종류와 게이팅

- 코멘트는 `general | question | decision | review_request` 종류와 `resolved` 상태를 가진다. 원문 파일은 불변이며, `resolved` 전환·수정·삭제는 같은 코멘트의 `.ops.jsonl`에 후속 op로 append하고 **현재 상태는 op 재생으로 계산**한다(§5.3).
- **미해결 `question` 또는 `review_request`가 있으면** 해당 이슈의 자동 claim과 `DONE` 전환을 차단한다(사람이 해제 가능). 사람의 질문이 활동 피드에 묻힌 채 에이전트가 계속 진행하는 상황을 막는다.

### 6.4 권한 scope

- 역할: `admin`(전체) / `member`(쓰기) / `agent`(토큰 scope에 종속).
- PAT는 **프로젝트 범위 + scope 목록**을 갖는다: `issue:read`, `issue:comment`, `issue:transition`, `issue:edit`, `issue:rank`, `run:write`, `issue:delete`.
  - 기본 에이전트 토큰 권장 조합: `issue:read`, `issue:comment`, `issue:transition`, `run:write`.
  - **`issue:delete`와 `issue:rank`(우선순위 변경)는 사람 전용**이며 에이전트 기본 scope에서 제외한다(D9). 필요하면 토큰별로 명시 부여한다.
- 토큰은 `expires_at`, `last_used_at`을 관리하며, 폐기 즉시 401이 된다.

## 10. 완료 기준 (Acceptance Criteria)

- **AC1** 이슈 생성 → `.localjira/issues/` 에 파일 생성, `git status`에 이슈 파일 1개만 잡힌다.
- **AC2** 5,000 이슈 + 스프린트 + 코멘트(resolve op 포함) + run fixture에서 `.local/index.sqlite` 삭제·재기동 → 삭제 전후 API 응답이 정규화 비교로 동일하다(제외: 검색 score, 인덱싱 시각, claim/lease 등 런타임 상태).
- **AC3** 에디터로 이슈 파일 직접 수정 → 상세 화면을 연 상태에서 **새로고침 없이 3초 이내** 반영되고, 이벤트가 `actor_kind=external`로 기록된다.
- **AC4** 카드 1개를 중간·최상단·최하단으로 이동 시 각각 변경 파일이 **1개**다. 동일한 두 카드 사이 1,000회 반복 삽입 후에도 순서가 안정적이며, 재균형 발생 시 그 사실이 로그에 남는다.
- **AC5** 스프린트 시작 → 보드에 스코프 표시. capacity 초과는 경고만 뜨고 시작을 막지 않는다. 종료 시 미완료 이슈 이월 선택지가 뜬다.
- **AC6** 에이전트 토큰으로 상태 변경 → 성공하며 타임라인에 `agent` 배지 + `run_id` + `initiated_by`가 함께 기록된다.
- **AC7** 권한 없는 역할의 쓰기 요청은 403.
- **AC8** 동일 ETag `E1`을 읽은 두 클라이언트가 서로 다른 title로 PUT → 첫 요청 200 + 새 ETag `E2`, 두 번째 **412** + 현재 ETag·현재 문서 전문·거부된 요청 값. 첫 변경은 보존된다. `If-Match` 없이 보낸 수정 요청은 **428**이며 파일을 바꾸지 않는다.
- **AC9** *(D16으로 대체)* 에이전트 토큰으로 이슈를 적재하면 `created_by_kind=agent`로 기록되고 카드·상세에 배지가 뜬다. 그 이슈는 `BACKLOG`이므로 **같은 에이전트가 claim하면 `E_CLAIM_NOT_REFINED`로 거부**되며, 사람이 `TODO`로 올린 뒤에만 착수 가능하다. 적재된 파일은 미커밋으로 남고 배지 건수가 증가한다 — 서비스는 커밋하지 않는다.
- **AC10** 손상된 이슈 파일·conflict marker 파일이 각 1건 있어도 나머지는 정상 동작하고, 배너에 파일 경로가 표시되며 해당 엔티티 변경은 차단된다.
- **AC11** 팀원 A의 생성·수정·삭제가 fast-forward pull 후 재기동 없이 반영된다. 1,000파일 대량 checkout과 워처 이벤트 overflow 후에도 조정 결과가 최종 파일 상태와 일치한다.
- **AC12** `epic`에 `subtask`를 직접 매달거나 계층 순환을 만들면 400. 하위가 있는 부모를 `strategy` 없이 삭제하면 409, `promote`면 하위가 최상위로 승격되고, `cascade_cancel`이면 하위가 `CANCELLED`가 된 뒤 부모가 삭제된다.
- **AC13** 5,000건에서 상태·라벨·claimable 복합 필터와 본문 전문 검색이 N1 기준을 만족한다.
- **AC14** 보드에서 §5.2 표에 없는 전이를 시도하면 400이며 카드가 원위치로 되돌아간다.
- **AC15** 파일 교체·인덱스 upsert·이벤트 기록 각 단계에 fault injection 후 재기동 → 파일이 부분 YAML 없이 완전한 상태이고, 누락된 인덱스·이벤트가 outbox 재생으로 복구된다.
- **AC16** 폐기된 PAT는 즉시 401. `issue:comment`만 가진 PAT의 상태 변경·삭제·rank 변경은 403이고 코멘트만 성공하며, 성공·거부 모두 token_id와 함께 감사된다.
- **AC17** N7 감사 범위의 각 행위가 이벤트로 남고, 타임라인에서 actor_kind가 구분 표시된다.
- **AC18** 동일 `Idempotency-Key`로 이슈 생성·코멘트를 재전송하면 최초 결과가 반환되고 중복 엔티티·중복 이벤트가 생기지 않는다.
- **AC19** 두 에이전트가 같은 이슈를 동시에 claim → 하나만 200, 나머지는 409. `blocked_by` 미완료 이슈와 `BACKLOG` 상태 이슈의 claim은 사유와 함께 거부된다. claim 없는 에이전트가 `IN_PROGRESS`로 전이하면 `issue:transition` scope가 있어도 403이다.
- **AC20** heartbeat 중단 후 lease 만료 → run이 `STALE`로 표시되고 claim이 회수 가능해진다. 사람이 강제 해제·run 취소하면 그 run의 후속 쓰기는 409이며 사유·수행자가 기록된다.
- **AC21** 작업 컨텍스트 API가 ETag·목표·인수조건·의존성·최신 사람 지시·허용 범위를 구조화해 반환한다.
- **AC22** 미해결 `question`이 있는 이슈는 자동 claim과 `DONE` 전환이 차단되고, 해결 처리 후 허용된다.
- **AC23** 번다운이 CANCELLED·무추정 이슈를 분모에서 제외하고, 스프린트 중 스코프 증감이 별도 선으로 표시된다.
- **AC24** 이슈를 만든 뒤 커밋하지 않으면 상단 배지에 미커밋 건수가 증가하고, `git -C .localjira commit` 후 0으로 돌아간다. 서비스가 스스로 커밋·푸시하지 않는다.
- **AC25** 두 클론이 오프라인에서 각각 `LJ-13`을 만든 뒤 머지 → 나중에 만들어진 쪽이 `LJ-14`로 재키잉되고, `LJ-13`으로 조회·링크 참조 시 두 이슈가 구분되어 해석된다(alias는 원 소유자 우선). 재키잉 사실이 이벤트로 남는다.
- **AC26** 코드 브랜치를 전환하거나 다른 워크트리에서 서버에 접속해도 동일한 보드·동일한 ACTIVE 스프린트가 보인다.

### D16 — AI 정제를 제품에 넣지 않는다 (2026-07-31, Q10 종결)

| ID | 결정 | 근거 |
|---|---|---|
| **D16** | **R22(AI 백로그 정제)를 철회한다.** 제품은 LLM을 호출하지 않으며 `Proposal` 엔티티·`proposals/` 경로·정제 화면을 만들지 않는다. 같은 목적은 **에이전트가 기존 `POST /issues`로 백로그를 적재**해 달성한다 | 아래 |

**Proposal이 사려던 것은 "검토 없이 백로그에 들어와 일이 시작되는 것"을 막는 관문 하나다.
그 관문이 이미 세 개 있다.**

1. **`BACKLOG`는 claim할 수 없다**(§6.1). 에이전트가 100건을 적재해도 사람이 `TODO`로 올리기
   전에는 아무것도 시작되지 않는다. 거부 코드 이름부터 `E_CLAIM_NOT_REFINED`다 — 이 가드는
   정제를 염두에 두고 만들어졌고, 정제 없이도 그대로 성립한다.
2. **미커밋 파일이 곧 초안이다**(D4·R25). 서비스는 커밋하지 않으므로 적재 결과는 미커밋으로
   남고, `git diff`로 통째로 검토하고 `git checkout`으로 통째로 버릴 수 있다. Proposal YAML을
   한 건씩 넘겨보는 것보다 넓은 검토면이다.
3. **`created_by_kind=agent` 배지**(§8). 만든 주체가 파일에 그대로 박히므로 사람이 쓴 것과
   섞이지 않는다. *(→ S6-D5: 화면이 이 값을 그리지 않고 있었다. 2026-08-03 고쳤다.)*

**그리고 이쪽 산출물이 낫다.** 정제 API는 붙여넣은 텍스트만 본다. 에이전트는 코드베이스·PRD·
기존 스토리·프로젝트 규약을 읽고 쓴다. 같은 요구사항으로 나오는 스토리의 질이 다르다.

**부수 효과.** 제품에서 외부 네트워크 호출이 0개로 유지된다(N4가 정제만 예외로 두던 것이
사라진다). API 키 보관·비용 상한·타임아웃·재시도·전송 범위·provenance가 전부 제품의 문제가
아니게 되고, 그것이 곧 **Q10의 종결**이다 — 전송하지 않는 것에는 전송 정책이 필요 없다.

**대가로 지는 것 둘.** ⓐ 에이전트를 쓰지 않는 사람은 문서를 붙여넣어 스토리를 얻을 수 없다.
이 제품의 대상 사용자가 "AI 에이전트와 일하는 사람"이므로 감수한다. ⓑ 에이전트가 잘못 만든
이슈를 **웹에서 지울 수 없다**(현재 삭제는 CLI 전용). 이 대가가 `r01e`를 P1으로 올린 이유다.

**S6-D5 — 카드와 상세에 "AI 유래" 표시를 따로 둔다 (2026-08-03).** E2E로 한 바퀴 돌려 보니
화면이 `created_by_kind`를 **한 번도 그리지 않고** 있었다. 카드 배지는 `last_actor_kind`만
보여 주는데, 사람이 손대는 순간 그 값이 `human`이 된다 — 그리고 그 "손대는 것"이 바로 D16이
세운 관문(사람이 `TODO`로 올리기)이다. **분류를 마치는 순간 출처가 카드에서 사라졌다.**

정보가 없어진 것은 아니다. 파일에 남아 있고 활동 타임라인에도 `issue.created 에이전트`가
있으므로 관문 ②(미커밋 검토)는 온전했다. 다만 D16이 세 번째 관문으로 **이름을 댄 그 배지**가
분류하는 사람이 실제로 보는 자리에는 없었다. 근거를 대고 기능 하나를 철회했으면 그 근거가
화면에 실제로 있어야 한다.

마지막 변경 주체 배지와 **다른 모양**으로 둔다 — 하나는 "누가 마지막에 바꿨나", 다른 하나는
"이건 어디서 왔나"이고, 같은 모양이면 같은 주장으로 읽힌다.

### S6-D6 — 데스크톱 창은 Electron이 아니라 `.app` + 브라우저 앱 모드다 (2026-08-03)

"아이콘을 눌러 창으로 보고 싶다"는 요청에 Electron·Tauri가 곧바로 떠오르지만, 그 순간 이 제품은
**런타임 하나를 배포·갱신·감사해야 하는 물건**이 된다 — UI를 바닐라로 쓰고 테스트를 `node:test`로
쓴 이유(S2-D1)가 통째로 사라진다.

`.app`은 plist와 실행 파일이 든 디렉터리라 `fs`로 쓸 수 있고, 창은 macOS가 이미 갖고 있는
`WKWebView`로 만들어 `swiftc`로 그 자리에서 컴파일한다. 100KB 남짓한 바이너리에 시스템
프레임워크만 쓴다. 아이콘도 `node:zlib`로 PNG를 써서 그린다.

**처음에는 Chromium의 `--app` 모드로 만들었고, 그것은 틀렸다.** Finder에서는 이름도 아이콘도
맞는데 **실행하면 독에 "Google Chrome"이 뜬다** — ⌘Tab도 그렇다. 브라우저를 여는 바로가기지
앱이 아니었고, 빌드는 어느 쪽을 만들었는지 말하지도 않았다. 사용자가 "그렇게 만든 거 맞냐"고
물어 확인하다 드러났다.

대가는 둘이다. ⓐ 네이티브 창에는 Xcode 명령줄 도구가 필요하다(없으면 브라우저 앱 모드로
물러나고, 빌드가 그렇게 말한다). ⓑ macOS 전용이다. 둘 다 문서에 적어 두고 감추지 않는다.

서버 수명은 그 창 인스턴스에 묶되, **앱이 띄우지 않은 서버는 앱이 끄지 않는다** — 터미널에서
`serve` 중인 사람이 창을 닫았다고 서버를 잃으면 안 된다. `r27`이 이 결정의 스토리다.

**전제 조건.** 적재 주체가 `agent`로 기록되어야 배지 근거가 성립하는데, 현재 `localjira issue
create`는 세션이 없어 actor를 `{id:"local", kind:"human"}`으로 고정한다. 에이전트가 CLI를
쓰면 **AI 산출물이 사람이 쓴 것으로 기록된다.** 그래서 적재는 PAT를 실은 HTTP API로 해야
하며, CLI에도 토큰 인증을 붙이는 것이 `r13c`다.

> 나머지 `⚠ 미정` **113건**은 각 스토리 파일 안에 남겨 두었다. API 세부 스키마·UI 문구·임계치 기본값 등
> **설계 단계(`3_designs/`)에서 정하면 되는 것들**이며 M1 착수를 막지 않는다.
> 분포는 M1 23건 · M2 20건 · M3 15건 · M4 14건 · **M5 41건**이었고, M5에 몰린 것은 Q10(LLM 전송
> 정책)이 미결이라 R22~R24가 전제를 세우지 못한 탓이었다. **D16이 R22를 철회하면서 그중 16건이
> 질문째로 사라졌다** — 답을 찾은 것이 아니라 답할 일이 없어진 것이다.
