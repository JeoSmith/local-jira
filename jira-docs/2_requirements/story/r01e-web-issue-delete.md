# 웹 이슈 삭제 — 확인 절차와 하위 처리 전략

> `r01c`(생성)·`r01d`(수정)의 마지막 짝이다. `r01b`가 `DELETE /issues/{key}`와 하위 처리
> `strategy`를 만들었지만 **화면에서 이슈를 지울 방법이 없다.** 지우려면 터미널을 열어야 한다.
>
> 두 스토리가 이것을 "파괴적 행위라 확인 절차 설계가 따로 필요하다"며 범위 밖으로 미뤘고, 그
> 판단 자체는 맞았다. 미뤄 둔 설계를 이제 한다.
>
> **P1으로 올린 이유는 D16이다.** AI 정제를 철회하고 에이전트가 백로그를 직접 적재하기로
> 하면서, "에이전트가 잘못 만든 이슈를 사람이 치운다"가 상시 경로가 됐다. 커밋 전이면
> `git checkout`으로 되돌릴 수 있지만 커밋한 뒤에 발견하면 CLI뿐이다. **D16이 감수하기로 한
> 두 대가 중 하나가 이것이고, 이 스토리가 그것을 갚는다.**

## 사용자 스토리 (User Story)

> **As a** 에이전트가 적재한 백로그를 훑다 쓸모없는 이슈를 발견한 개발자·PO,
> **I want** 그 자리에서 지우되 **무엇이 함께 사라지는지 보고 나서** 지우기를,
> **so that** 터미널로 옮겨 가지 않으면서도, 하위 이슈가 딸린 부모를 무심코 지워
> 모르는 사이에 트리를 잃지 않는다.

## 인수 조건 (Acceptance Criteria)

### 지우기

- [x] Given 이슈 상세, When [삭제]를 누르면, Then **확인 단계 없이 바로 지워지지 않고** 확인 대화가 뜬다. 파괴적 행위에 실행 취소가 없으므로 확인이 유일한 방어선이다.
- [x] Given 확인 대화, When 내용을 보면, Then **지울 이슈의 키와 제목**이 표시된다 — "정말 삭제하시겠습니까?"만 띄우면 무엇을 지우는지 화면이 말해 주지 않는다.
- [x] Given 확인 대화, When [취소]를 누르거나 `Esc`를 누르면, Then 아무 요청도 보내지 않고 닫히며 포커스가 열기 직전 요소로 돌아간다. *(r01c·r01d와 같은 규약)*
- [x] Given 삭제 성공, When 화면을 보면, Then 목록·보드가 갱신되고 상세가 닫히며, 삭제된 이슈로 돌아가지 않는다.
- [x] Given 삭제 요청, When 헤더를 확인하면, Then 상세를 읽을 때 받은 **그 ETag가 `If-Match`로** 실린다. 열어 둔 사이 남이 고쳤으면 **412**를 받고 지우지 않는다. *(D15 — 내가 본 것과 다른 것을 지우지 않는다)*

### 하위가 있을 때 (§5.1 계층, r01b `strategy`)

- [x] Given 하위 이슈가 있는 부모, When [삭제]를 누르면, Then 확인 대화에 **하위 건수**가 표시되고 `promote`(하위를 최상위로 승격)·`cascade_cancel`(하위를 `CANCELLED`로) 중 **사람이 고르기 전에는 진행되지 않는다.** 어느 쪽도 기본 선택이 아니다. *(AC12)*
- [x] Given `strategy` 없이 보낸 요청, When 서버가 409를 돌려주면, Then 그 사유를 대화 안에 표시하고 선택지를 제시한다 — 클라이언트가 규칙의 사본을 갖지 않는다.
- [x] Given `cascade_cancel` 선택, When 처리하면, Then 하위가 `CANCELLED`가 된 뒤 부모가 삭제되고, **몇 건이 취소됐는지** 결과로 표시된다. *(AC12)*
- [x] Given `promote` 선택, When 처리하면, Then 하위가 최상위로 올라가고 목록에 그대로 남는다.

### 거부 경로

- [x] Given `issue:delete` scope가 없는 역할·토큰, When 상세를 보면, Then [삭제]가 노출되지 않거나 비활성이다 — 눌러서 403을 받는 경험을 만들지 않는다. *(§6.4, AC7)*
- [x] Given 에이전트 기본 토큰, When scope를 확인하면, Then `issue:delete`가 **없다**. 에이전트가 자기가 만든 것을 스스로 지울 수 없어야 사람의 검토가 관문으로 남는다. *(D9)*
- [x] Given 타인의 유효 claim이 걸린 이슈, When 삭제를 시도하면, Then 경고와 함께 강제 여부를 확인받는다 — 남이 지금 작업 중인 것을 조용히 지우지 않는다. *(§6.1)*
- [x] Given `INVALID`로 격리된 이슈, When [삭제]를 시도하면, Then 격리 상태와 파일 경로가 표시된다. *(§5.6)*

### 그 밖

- [x] Given 삭제 후, When `git -C .localjira status`를 보면, Then 파일 삭제가 미커밋으로 잡히고 배지 건수가 증가한다 — **서비스는 커밋하지 않으므로 커밋 전이면 `git checkout`으로 되살릴 수 있다.** 이것이 실행 취소를 별도로 만들지 않는 근거다. *(D4, R25)*
- [x] Given 삭제 후, When 활동 타임라인을 보면, Then `issue.deleted` 이벤트가 남고 actor가 사람으로 표기된다. *(§9 N7, R14)*
- [x] Given 라이트/다크 테마, When 확인 대화를 열면, Then 두 테마 모두에서 기존 규약으로 렌더되고 의존성 0개 바닐라를 유지한다. *(S2-D1)*
- [x] Given 네트워크가 없는 환경, When 이슈를 지우면, Then 정상 동작한다. *(N4)*

> **S6-D1 — 확인에 타이핑을 요구하지 않는다.** 제목을 받아 적게 하는 방식은 **되돌릴 수 없는**
> 행위에 쓰는 장치다. 여기서는 서비스가 커밋하지 않으므로(D4) 커밋 전이라면 `git checkout`으로
> 통째로 되돌아온다 — 대화에 그 명령을 적어 둔 이유다. 대신 강도는 **하위 건수에 따라 저절로**
> 갈린다: 하위가 없으면 [삭제] 한 번, 있으면 전략을 고르는 두 번째 결정을 지나야 하고 그
> 전략은 기본 선택이 없다. 타이핑을 붙이면 에이전트 적재분 정리(D16이 만든 상시 경로)가
> 고역이 되어 사람이 화면을 버리고 CLI로 간다.
>
> **S6-D2 — 일괄 삭제는 만들지 않는다.** D16 이후 "적재분을 한 번에 치우는" 수요가 생길 수는
> 있지만, 아직 한 번도 써 보지 않았다. 되돌리기 어려운 행위의 반경을 수요가 확인되기 전에
> 넓히지 않는다. 필요해지면 그때 별 스토리로 열고, 그때도 처리는 건 단위여야 한다.

> **만들다 나온 것(2026-08-03).** 이 스토리는 화면 하나를 붙이는 일이었는데, 붙일 자리를
> 확인하다 **이미 있다고 적혀 있던 것 셋이 없다는 사실**이 드러났다. 넷 다 이 브랜치에서 고쳤다.
>
> **① 포커스 트랩이 없었다.** `r01c`·`r01d`가 "Tab 포커스가 폼 밖으로 새지 않는다"를 각각
> 인수조건으로 걸고 **둘 다 체크돼 있었는데**, 브라우저에서 Tab을 일곱 번 누르니 열린 생성 폼을
> 빠져나가 툴바의 [내보내기]에 포커스가 갔다. 키보드 사용자가 보이지 않는 컨트롤을 조작할 수
> 있는 상태였다. 모달 셋이 공유하는 트랩 하나를 만들고 `role="dialog"`·`aria-modal`을 붙였다 —
> 세 번 잊을 기회를 한 번으로 줄이는 편이 낫다.
>
> **② `Esc`가 상세 패널까지 닫았다.** keydown 처리기가 둘이었고 뒤엣것이 `state.detail`만 보고
> 닫았다. 모달을 연 채 `Esc`를 누르면 대화와 패널이 함께 닫히고, 대화가 되돌려 줄 포커스는 이미
> 사라진 뒤였다. `r01d`의 같은 인수조건이 이걸 못 잡은 건 **폼은 정말로 닫혔기** 때문이다.
>
> **③ `--card`가 정의된 적이 없었다.** 일곱 곳에서 쓰는데 선언이 없어 커맨드 팔레트·생성 폼·
> 수정 폼이 전부 **배경이 투명**했다. 반투명 백드롭 너머로 뒤 화면이 비쳤다.
>
> **④ `cascade_cancel`이 매번 격리 이슈를 만들었다.** 하위를 `CANCELLED`로 바꾸기만 하고
> **부모 참조를 그대로 두어**, 부모 파일이 사라지는 순간 R11이 `dangling_ref`로 격리했다.
> 문서에 적힌 삭제 방법이 쓸 때마다 보드를 INVALID로 만들고 있었다. 기존 테스트가 못 잡은
> 이유는 격리된 이슈도 마지막 정상 행으로 `GET`에 200을 주고 `status`도 `CANCELLED`로 읽히기
> 때문이다 — **셋 다 통과하는 동안 아무도 보드를 보지 않았다.** 두 전략 모두 부모를 끊도록
> 고치고, 파일과 `/integrity/issues`를 함께 확인하는 단언을 넣었다.
>
> **덤으로 만든 것.** claim을 읽을 경로가 **보드 응답뿐**이었다(활성 스프린트 한정). 백로그에서
> 지우는 사람은 누가 그 이슈를 붙잡고 있는지 알 길이 없었다. `GET /issues/{key}/claim`을 냈다 —
> 이슈 표현에 넣지 않은 이유는 그 바이트가 ETag라서(D15), 에이전트가 claim을 잡을 때마다
> 편집자들의 `If-Match`가 아무 변경 없이 무효가 되기 때문이다. 그 사실 자체를 테스트로 걸었다.

## 범위 밖 (Out of Scope)

- 삭제 API·`strategy` 규칙 자체 — `r01b`가 만들었다. 이 스토리는 화면이다
- 실행 취소(undo) — 미커밋 상태의 `git checkout`이 그 역할을 한다(D4). 앱 안에 별도 undo 스택을 두면 파일 SoT 밖에 두 번째 진실이 생긴다
- `CANCELLED` 전이 — 삭제가 아니라 상태 변경이고 전이 엔드포인트 소관이다(S1-D2)
- 스프린트·코멘트·첨부 삭제 — 각각 별 요구사항이다
