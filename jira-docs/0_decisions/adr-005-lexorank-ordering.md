# ADR-005 — LexoRank와 `(rank, uid)` 결정적 정렬

- 상태: accepted
- 일자: 2026-07-27
- 결정: PRD §5.1·§5.7, R3·R7
- 관련: [ADR-001](adr-001-file-sot-sqlite-index.md) · [ADR-006](adr-006-shared-board-data-branch.md)

## Context

정수 position으로 백로그 중간에 항목을 넣으면 뒤의 많은 이슈 파일을 한꺼번에 다시 번호 매겨야 한다.
파일 SoT를 git으로 공유하는 환경에서는 사소한 드래그가 큰 diff와 merge 충돌을 만든다.

LexoRank 같은 희소 문자열 rank는 보통 이동 대상 파일 하나만 바꾸지만 충돌이 완전히 사라지지는 않는다.
두 클론이 같은 간격에 삽입하면 같은 rank가 생길 수 있고, 인접 rank 사이 공간이 소진되면 여러 항목을
재균형해야 한다. 중복 rank를 무결성 오류로 격리하면 정상 git merge가 보드를 멈춘다.

백로그 순서와 스프린트 보드 순서는 수명과 정렬 영역이 다르다. 하나의 rank를 공유하면 보드 이동이
백로그 우선순위를 뜻하지 않게 바꾼다.

## Decision

### 1. 순서 필드를 분리한다

- `backlog_rank`: 프로젝트 백로그 전체 순서. 스프린트에 들어가거나 나와도 보존
- `board_rank`: 정렬 영역 `(sprint_id, status)` 안의 카드 순서

모든 조회와 재균형의 최종 정렬 키는 `(rank, uid)`다. `uid`는 불변 ULID이므로 같은 rank가 생겨도
모든 클론이 같은 순서를 얻는다. 중복 rank는 오류나 격리 사유가 아니라 재균형 후보 신호다.

### 2. 일반 이동은 한 엔티티만 수정한다

이동 대상의 앞·뒤 rank 사이에 사전식으로 정렬되는 새 rank를 계산한다. 맨 앞·맨 뒤 삽입도 같은 rank
공간 규칙을 사용한다. 한 이동 요청은 target uid와 두 이웃 uid를 함께 보내며, 서버는 현재 인접 관계와
ETag를 mutex 안에서 다시 확인한다. stale 이웃이면 409/412로 거부하고 현재 순서를 반환한다.

동일 위치 요청이나 현재 순서를 바꾸지 않는 이동은 no-op으로 처리해 파일·이벤트를 만들지 않는다.
에이전트의 rank 변경은 `issue:rank` scope가 별도로 있어야 하며 기본 scope에는 포함하지 않는다(D9).

### 3. 공간 소진 시 결정적으로 구간 재균형한다

새 rank를 만들 수 없거나 rank 길이가 구현 상한을 넘으면 최소 연속 구간을 넓혀 균등 간격 rank를
다시 배정한다. 입력 snapshot을 `(기존 rank, uid)`로 정렬하고 같은 알고리즘·고정 alphabet·고정
precision을 사용해 모든 노드가 같은 결과를 만든다.

재균형은 프로젝트 단위 mutex 안에서 하나의 다중 파일 WriteTxn으로 처리하고, 모든 대상의 ETag와
영역 소속을 다시 확인한다. 하나라도 stale이면 전체를 적용하지 않고 새 snapshot으로 재계산한다.
재균형 결과가 동일한 경우 반복 실행은 no-op이다.

구체적인 alphabet, 초기 간격, 길이 상한과 최소 구간 확대 폭은 구현 상세 설계와 property test fixture로
고정한다. 이를 바꾸는 것은 저장 데이터 호환성 변경이므로 `schema_version`과 migration이 필요하다.

### 4. 외부 merge의 중복은 수용한다

git merge 뒤 동일 rank가 여러 개면 `(rank, uid)`로 즉시 정상 조회하고 background 재균형 대상으로
표시한다. 자동 재균형이 또 다른 외부 변경과 경합하면 ETag/CAS로 중단하고 다음 조정에서 다시 시도한다.
순서 안정성을 위해 uid tie-break 없이 파일 순서나 인덱스 삽입 순서에 의존하지 않는다.

## Alternatives

- **연속 정수 position** — 중간 삽입마다 대량 파일 변경과 충돌이 발생한다. 기각.
- **부동소수점 midpoint** — 정밀도 소진과 언어·직렬화 차이로 결정성을 증명하기 어렵다. 기각.
- **배열 하나에 모든 uid 저장** — 이동마다 공유 파일 한 곳이 충돌 hotspot이 된다. 기각.
- **생성 시각/ULID만으로 정렬** — 임의 재정렬을 표현할 수 없다. 기각.
- **중복 rank를 격리** — 정상적인 오프라인 merge를 운영 장애로 만든다. 기각.
- **백로그와 보드에 rank 하나 사용** — 보드 컬럼 이동이 백로그 우선순위를 뜻하지 않게 변경한다. 기각.

## Consequences

- (+) 일반 드래그는 보통 이슈 파일 하나만 바꿔 git diff와 충돌을 줄인다.
- (+) 중복 rank가 있어도 모든 클론이 같은 순서를 보여준다.
- (+) 백로그 우선순위와 보드 내 배치를 독립적으로 유지한다.
- (−) rank 생성·구간 재균형 알고리즘과 property test가 필요하다.
- (−) 공간 소진 시 여러 파일이 바뀌는 비용을 완전히 제거할 수 없다.
- (−) alphabet·precision 변경은 migration이 필요한 저장 형식 결정이다.
