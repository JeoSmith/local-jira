# ADR-006 — 공유 보드: 전용 데이터 브랜치 · git 전용 동기화 · 자동 재키잉

- 상태: accepted
- 일자: 2026-07-27
- 결정: PRD §13 **D1 · D2 · D3**
- 관련: [PRD](../2_requirements/prd/backlog-sprint.md) · ADR-002(단일 writer) · ADR-003(ETag 동시성) · ADR-004(claim/lease)

## Context

이슈 데이터를 파일로 두고 git에 얹는 순간, **"그 파일이 어느 브랜치에 사는가"** 가 제품의 의미를 결정한다.
이슈 파일이 코드와 같은 브랜치를 따라가면 다음이 전부 깨진다.

| 깨지는 것 | 구체적 증상 |
|---|---|
| 보드의 현재 상태 | `feat/a`에 있는 사람과 `feat/b`에 있는 사람이 서로 다른 백로그를 본다. "지금 뭐가 진행 중인가"에 답이 없다 |
| ACTIVE 스프린트 유일성 | 브랜치마다 ACTIVE가 하나씩 존재할 수 있다. §5.6의 "프로젝트당 1개" 불변조건이 무의미해진다 |
| claim / lease (ADR-004) | 다른 브랜치의 에이전트는 내 claim 파일을 보지 못한다. 선점이 성립하지 않아 중복 실행을 막을 수 없다 |
| ETag 동시성 (ADR-003) | 브랜치별로 파일 내용이 달라 같은 이슈가 여러 개의 "현재 버전"을 갖는다 |
| 단일 writer (ADR-002) | 워크트리마다 `.localjira`가 하나씩 생기고, 각자 서버를 띄우면 writer가 N개가 된다 |

동시에 이 프로젝트는 **병렬 워크트리 운용**(`.worktree/<주제>/`)을 전제한다. 한 사람이 워크트리 3개를 띄우고
각 워크트리에서 에이전트를 돌리는 것이 정상 사용 패턴이다. 브랜치 종속 배치는 이 패턴과 정면으로 충돌한다.

또한 팀 사용(로그인·역할)을 목표로 하면서도 **"로컬 우선"** 을 포기하지 않으려면, 상시 떠 있는 공유 서버 없이
데이터를 주고받아야 한다. 이 경우 두 사람이 오프라인에서 각각 이슈를 만들면 **같은 표시 키(`LJ-13`)가 두 개**
생기는 문제가 필연적으로 따라온다.

## Decision

**보드는 하나다. 데이터는 코드 브랜치를 따라가지 않고, 같은 저장소의 전용 orphan 브랜치에 산다.**

### D1 — 전용 데이터 브랜치 + worktree

`localjira/data` orphan 브랜치를 만들어 리포 루트 `.localjira/`에 worktree로 붙이고,
코드 브랜치 쪽 `.gitignore`에 `.localjira/`를 넣는다.

```bash
git switch --orphan localjira/data
git commit --allow-empty -m "init board"
git switch -
git worktree add .localjira localjira/data
echo ".localjira/" >> .gitignore
```

- 코드 브랜치를 아무리 오가도 `.localjira/`의 내용은 바뀌지 않는다 → **보드 상태가 하나**로 유지된다.
- 보드 커밋이 코드 히스토리에 섞이지 않고, 코드 리뷰 diff에도 잡히지 않는다.
- `.localjira/`는 **리포 루트 한 곳에만** 존재한다. 다른 워크트리의 사람·에이전트는 파일이 아니라 서버 URL로
  접근하므로 ADR-002의 단일 writer가 배치만으로 강제된다.

### D2 — 동기화는 git 전용

`git -C .localjira pull --rebase` / `push`로만 주고받는다. 상시 공유 서버를 두지 않는다.
오프라인 작업과 그로 인한 머지 충돌은 PRD §5.6의 격리(INVALID) 모델로 흡수한다.

### D3 — 표시 키 충돌은 결정적 자동 재키잉

머지 후 같은 표시 키를 가진 이슈가 둘이면 **`uid`(ULID)의 생성 시각이 나중인 쪽**이 새 키를 받는다.
이전 키는 `former_keys[]`에 남아 조회·링크·검색의 alias로 계속 동작한다.

- 새 키는 **머지된 전체 파일 집합에서 결정적으로 계산**한다(해당 프로젝트의 최대 키 번호 + 충돌 항목의 uid 정렬 순번).
- ULID에 생성 시각이 박혀 있고 계산 입력이 머지 결과 전체이므로, **두 클론이 각자 조정해도 같은 결과에 수렴**한다.
  중앙 조정자가 없어도 재키잉이 갈라지지 않는다 — 이것이 정수 시퀀스 대신 ULID를 내부 식별자로 쓰는 이유다.
- `uid` 자체가 중복된 경우는 어느 쪽이 원본인지 알 수 없으므로 **자동 해결하지 않고** 양쪽을 격리한다.

## Alternatives

- **대안 A — 이슈 파일을 코드 브랜치에 함께 둔다**
  (+) 요구사항 변경이 코드 PR diff에 함께 보인다. 설정이 필요 없다.
  (−) Context 표의 다섯 가지가 전부 깨진다. 특히 claim/ACTIVE 스프린트가 성립하지 않아 **제품의 핵심 가치(사람–AI 공동 보드)가 무너진다.** → 기각.
- **대안 B — 보드 전용 별도 저장소**
  (+) 관심사 분리가 가장 깨끗하고 접근 권한을 따로 줄 수 있다.
  (−) 클론이 2개가 되어 셋업·인증·백업이 두 벌이 된다. 개인·소규모 팀 도구에 과한 비용. → 기각(팀이 커져 보드 접근 권한을 코드와 분리해야 하면 그때 승격한다. `.localjira`가 이미 독립 worktree라 이전 비용은 낮다).
- **대안 C — 상시 공유 서버 한 대**
  (+) 키 충돌·머지 충돌이 원천적으로 없다. 실시간 동기화가 자연스럽다.
  (−) "로컬 우선"이 무너지고 그 서버가 단일 장애점이 된다. 서버가 죽으면 아무도 보드를 못 본다. → 기각.
- **대안 D — 정수 시퀀스 키 + 충돌 시 수동 해결**
  (+) 구현이 단순하다.
  (−) 오프라인 작업마다 사람이 개입해야 하고, 두 사람이 각자 다르게 해결하면 다시 갈라진다. → 기각(D3의 결정적 규칙으로 대체).

## Consequences

- (+) 브랜치·워크트리를 아무리 늘려도 보드는 하나다. ACTIVE 스프린트 유일성·claim·ETag가 모두 성립한다.
- (+) 단일 writer가 배치로 강제된다. 별도 잠금 프로토콜 없이 ADR-002가 지켜진다.
- (+) 보드 히스토리와 코드 히스토리가 분리되어 양쪽 로그가 깨끗하다.
- (+) 재키잉이 결정적이라 오프라인 작업 후 pull만 하면 사람이 손댈 일이 없다.
- (−) **셋업 한 단계가 추가된다.** 새 팀원은 클론 후 `git worktree add .localjira localjira/data`를 해야 보드가 보인다. → M0 부트스트랩 명령으로 자동화한다.
- (−) **`git clean -xdff`가 보드를 지울 수 있다.** `.localjira/`가 코드 쪽에서 ignore 대상이기 때문이다. → 완화: `localjira/data`를 원격에 push해 두면 worktree 재생성으로 복구된다. 서버는 기동 시 worktree 부재를 감지해 명확한 오류와 복구 명령을 출력한다.
- (−) 미커밋 보드 변경은 로컬 디스크에만 존재한다(PRD D5). → 완화: 미커밋 건수·마지막 push 시각을 UI 상단에 상시 노출한다(R25).
- (−) 표시 키가 바뀔 수 있다. → 완화: `former_keys[]` alias로 옛 키 조회가 계속 동작하고, 재키잉 사실을 이벤트로 남겨 설정 화면에서 이력을 볼 수 있다.
- 후속: 재키잉 규칙의 결정적 계산식과 alias 충돌 우선순위(같은 옛 키를 두 이슈가 갖는 경우)는 `3_designs/detailed/`에서 확정한다.
