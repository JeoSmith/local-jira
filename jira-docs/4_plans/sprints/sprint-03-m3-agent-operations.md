## 1. 목표

**에이전트가 이 보드의 1급 사용자가 된다.**

지금 에이전트가 할 수 있는 일은 없다. `agent` 역할은 `issue:read` 하나만 갖고 있고
(`src/auth/authorize.ts:45`), 토큰 발급 수단이 없으며, 두 에이전트가 같은 이슈를 동시에
집는 것을 막을 장치도 없다. 이 스프린트가 끝나면 다음이 성립한다.

1. 머신 계정에 PAT를 발급하고 언제든 끊을 수 있다.
2. 오작동한 에이전트가 우선순위를 뒤집거나 이슈를 지울 수 없다 — 구조적으로.
3. 두 에이전트가 같은 이슈를 동시에 집으면 정확히 하나만 성공한다.
4. 죽은 에이전트의 점유는 자동 회수되고, 사람은 언제든 뺏을 수 있다.
5. "이 이슈를 어떤 세션이 어느 브랜치에서 어디까지 했나"가 보드에서 보인다.

## 2. 이번 스프린트의 성격 — 앞의 둘과 다른 점

Sprint 01은 저장 코어(틀리면 조용히 데이터가 상한다), Sprint 02는 화면(틀리면 눈에 보인다)이
중심이었다. **이번은 권한과 동시성이다 — 틀리면 조용히 뚫린다.**

세 가지가 이전과 다르다.

**첫째, 거부가 기능이다.** 이 스프린트의 인수조건 중 상당수가 401·403·409를 요구한다.
"되는 것"보다 "안 되는 것"이 많고, 안 되는 것은 테스트로만 보인다. 성공 경로만 통과하는
테스트 묶음은 이 스프린트에서 아무것도 증명하지 못한다.

**둘째, 원자성이 단일 연산이어야 한다.** r16a AC2는 명시적으로 "조회 후 상태 변경 2단계로
구현하지 않는다"고 못박는다. 두 요청을 순서대로 보내 통과하는 테스트는 이 조건을 검증하지
못한다 — 진짜 동시 요청이 필요하다.

**셋째, 새 저장소가 하나 는다.** `.local/runtime.sqlite`는 파일 SoT도, 인덱스도, outbox도
아닌 네 번째 저장소다. 재빌드 대상이 아니고, git에 가지 않고, 재기동 시 만료분만 회수된다
(ADR-004 §1). 어디에 무엇을 두는지 헷갈리면 유령 점유가 클론 사이로 퍼진다.

## 3. 웨이브와 게이트

### Wave 1 — 토큰과 재시도 (10점)

`r13a` PAT 발급·폐기·만료 · `r15` 멱등성

에이전트가 존재하기 전에 갖춰야 하는 둘이다. 서로 의존하지 않아 병렬로 간다.

**Gate 1** — 발급한 PAT로 API를 호출하고, 폐기 직후 같은 토큰이 401이 된다. 같은
`Idempotency-Key`로 두 번 보낸 생성 요청이 엔티티도 이벤트도 하나만 남긴다. 서버를
재기동해도 그렇다.

### Wave 2 — scope 강제 (5점)

`r13b` PAT 프로젝트 범위·scope 강제

**Gate 2** — `issue:comment`만 가진 토큰이 코멘트는 쓰고 전이·삭제·rank 변경은 각각 403이다.
성공과 거부가 **양쪽 다** `token_id`와 함께 감사에 남는다. 거부된 요청은 `.localjira/` 아래
어떤 파일도 건드리지 않는다.

### Wave 3 — 실행과 선점 (13점)

`r17a` AgentRun 생명주기 · `r16a` 이슈 선점과 전이 강제 결합

**한 웨이브로 묶는 이유**는 ADR-004 §2다. claim을 저장할 때 유효한 `run_id`가 반드시
존재해야 하므로 run이 먼저 서야 하는데, r17a의 인수조건 두 개(카드의 claim 소유자 배지,
STALE run 회수 후 재선점 가능)는 claim이 있어야 닫힌다. 나눠 놓으면 어느 쪽도 "완료"라고
말할 수 없다.

**Gate 3** — 두 에이전트가 같은 이슈에 **동시에** claim을 던지면 정확히 하나가 200이고
나머지가 409다. claim 없는 에이전트의 `IN_PROGRESS` 전이는 `issue:transition` scope가
있어도 403이다. `BACKLOG` 이슈와 미완료 `blocked_by`를 가진 이슈는 사유 코드와 함께 거부된다.

### Wave 4 — 수명과 결과 (8점)

`r16b` lease·heartbeat·강제 해제 · `r17b` 구조화 결과 제출

**Gate 4** — heartbeat를 끊은 claim이 15분 뒤 다른 에이전트에게 넘어간다. 사람이 강제
해제한 뒤 그 run이 보낸 쓰기는 409다. 종료 시 다섯 필드를 하나라도 빠뜨리면 400이고 run은
종료되지 않는다.

## 5. 결정

### 이미 닫혀 있던 것 — 새로 열지 않는다

스토리 파일의 "⚠ 미정" 중 셋은 PRD와 ADR에 이미 답이 있었다.

| 스토리의 질문 | 실제로는 | 근거 |
|---|---|---|
| 에이전트의 `TODO`·`BLOCKED`·`CANCELLED` 전이에 claim이 필요한가 | 아니다. claim은 `IN_PROGRESS`·`IN_REVIEW`·`DONE` 셋에만 강제된다 | ADR-004 §2, PRD §6.1 |
| `project_scope`가 여러 프로젝트를 담는가 | 단수 필드다 | PRD §5.1 Token 엔티티 |
| claim의 `run_id`를 claim이 발급하는가, 요청이 제출하는가 | 제출한다. 임시·NULL run으로 소유권을 만들지 않는다 | ADR-004 §2 |

### S3-D1 — run이 claim보다 먼저다 *(2026-07-29)*

ADR-004 §2가 "claim 저장 시점에는 유효한 `run_id`가 반드시 존재해야 한다"고만 하고 순서를
M3 상세 설계로 미뤘다. 여기서 닫는다.

**`POST /runs`로 run을 먼저 만들고, `POST /issues/{id}/claim`이 그 `run_id`를 본문에 담는다.**

반대 순서(claim이 run을 발급)는 claim 하나에 run 하나가 강제로 묶여, 한 에이전트가 여러
이슈를 순차로 처리하는 흔한 경우에 run이 이슈마다 쪼개진다. §6.2가 run에 등록하라는 것은
`session_id`·`agent_id`·`initiated_by`·`branch`이고 전부 이슈가 아니라 **실행**의 속성이다.

따라서 **한 이슈에 여러 run이 붙을 수 있고**(이력), **한 run이 여러 이슈를 거칠 수 있다.**
동시에 유효한 claim은 이슈당 하나다.

### S3-D2 — run의 `state`는 넷, STALE은 계산이다 *(2026-07-29)*

PRD는 `STALE`만 명시하고 나머지를 규정하지 않았다.

저장하는 값은 **`RUNNING` · `DONE` · `FAILED` · `CANCELLED`** 넷이다. `STALE`은 저장하지
않는다 — ADR-004 §3이 "조회 시각과 `last_heartbeat_at`으로 계산한다"고 정했고, 저장하면
그 값을 갱신할 주체가 필요해진다(누가 3분마다 스캔하는가). 계산하면 그 질문이 사라진다.

`DONE`과 `FAILED`를 나누는 이유는 r17b AC10이다. 결과를 제출하지 못하고 끝난 run이 정상
종료와 구분되어 보여야 한다.

### S3-D3 — heartbeat는 run 단위 하나다 *(2026-07-29)*

§6.1은 claim의 lease를, §5.1/§6.2는 run의 `last_heartbeat_at`을 말하고 API 분리 여부를
규정하지 않는다.

**`POST /runs/{run_id}/heartbeat` 하나**로 두 가지를 함께 한다: run의 `last_heartbeat_at`을
갱신하고, 그 run이 쥔 claim의 `lease_expires_at`을 `now + 15분`으로 민다.

엔드포인트를 둘로 나누면 에이전트가 하나만 보내는 상태가 생기고, 그때 run은 살아 있는데
claim은 만료되거나 그 반대가 된다. 살아 있음을 보고하는 주체는 실행 중인 프로세스 하나이므로
신호도 하나여야 한다.

### S3-D4 — 같은 키에 다른 페이로드는 409다 *(2026-07-29)*

PRD 미규정. 최초 응답을 그대로 돌려주는 선택지가 있으나 **거부한다**.

같은 키로 다른 내용을 보낸 것은 재시도가 아니라 클라이언트의 버그다. 최초 응답을 돌려주면
두 번째 요청은 **조용히 버려지고** 클라이언트는 성공했다고 믿는다. 이 프로젝트가 이번
세션에 세운 규칙 — 검증은 거짓말할 수 없어야 한다 — 이 그대로 적용된다.

**409 `E_IDEMPOTENCY_KEY_REUSED`**, 본문에 최초 요청의 지문(요청 본문의 정규 JSON 해시)을
담는다. 판정은 정규 JSON(RFC 8785) 해시 비교이므로 키 순서나 공백 차이로 오탐하지 않는다.

처리 중인 키에 같은 요청이 겹쳐 도착하면 **409 `E_IDEMPOTENCY_IN_PROGRESS`**다. 단일 writer라
어차피 직렬화되지만, 기다리게 하면 대기 시간이 락 대기와 구분되지 않는다.

키 형식은 **1–255자 인쇄 가능 ASCII**, 벗어나면 400이다.

### S3-D5 — claim 거부는 전부 409이되 사유 코드가 다르다 *(2026-07-29)*

PRD는 `BACKLOG`·미완료 `blocked_by` 거부를 "사유와 함께"로만 규정한다.

**상태코드는 409로 통일**하고 본문의 `code`로 가른다: `E_CLAIM_HELD`(타인 점유) ·
`E_CLAIM_NOT_REFINED`(BACKLOG) · `E_CLAIM_BLOCKED`(미완료 `blocked_by`).

셋 다 "지금은 안 되지만 조건이 바뀌면 된다"는 같은 성질이다. 403으로 하면 권한 문제로
읽히고, 400으로 하면 요청이 잘못됐다는 뜻이 되는데 둘 다 사실이 아니다.

### S3-D6 — 제출된 run 결과는 고치지 않는다 *(2026-07-29)*

PRD 미규정. 코멘트와 달리 run 결과에는 후속 op 모델이 없다.

**한 번 제출하면 불변이다.** 결과는 "그때 그 실행이 무엇을 했다고 보고했는가"의 기록이고,
나중에 고칠 수 있으면 그 기록이 증거로서 쓸모가 없다. 정정은 이슈 코멘트로 남긴다.

같은 이유로 제출된 커밋 해시를 저장소에서 **검증하지 않는다**. 기록만 한다 — 커밋 연결
자동화는 R23(M5)이다.

"검증 통과 여부"는 불리언이 아니라 **`passed` · `failed` · `skipped` 열거**다. r17b AC4가
"검증을 수행하지 않은 사실이 명시적으로 담겨야 한다"고 요구하는데, 불리언에는 그 자리가 없다.

### S3-D7 — 기본 90일, 무기한도 허용한다 *(2026-07-29, r13a)*

PRD는 `expires_at` 필드 존재만 규정한다.

**발급 시 기본 90일. 상한은 두지 않으며 무기한(`expires_at: null`) 토큰을 허용한다.**

CI나 상시 데몬처럼 사람이 갱신하러 갈 수 없는 자리가 있고, 거기에 만료를 강제하면 결국
누군가 만료 직전에 수동으로 미루는 절차가 생긴다. 그 절차는 잊히고, 잊히면 에이전트가
한밤중에 401을 받는다. D5가 "PAT는 기기별 재발급이 정상 경로"라고 한 것은 백업 비대상이라는
뜻이지 수명을 짧게 하라는 뜻이 아니다.

대신 무기한 토큰이 조용히 쌓이지 않게 두 가지를 강제한다.

- `/settings`의 PAT 목록에서 무기한 토큰은 만료일 자리에 **"무기한"으로 시각적으로 구분**되어
  보인다. 날짜 칸이 빈 채로 지나가면 안 된다.
- `last_used_at`이 이 정책의 안전장치다. 만료가 걸러주지 않는 이상, "쓰이지 않는 토큰을
  알아본다"는 r13a의 사용자 스토리를 실제로 지탱하는 것은 최근 사용 시각뿐이다. 목록에서
  이 열은 선택이 아니다.

### S3-D8 — 본인 토큰은 `member`도 발급한다 *(2026-07-29, r13a)*

현재 `token:manage`는 admin 전용이다(`authorize.ts:26`).

**`member`는 자기 계정의 토큰을 발급·폐기할 수 있다. 다른 사람 계정의 토큰은 `admin`만
발급한다.**

에이전트를 돌리는 사람이 admin에게 요청해야 한다면 실무에서는 admin 계정 공유로 이어진다.
반대로 `member`에게 타인 토큰 발급까지 열어 주면, 남의 이름으로 감사 기록을 남길 수 있게
되어 "누가 바꿨는지는 항상 구분되어 표시된다"(PRD §1)와 정면으로 충돌한다.

따라서 `token:manage`를 대상 기준으로 가른다. 자기 대상이면 `member` 이상, 타인 대상이면
`admin`. 능력 표에 축이 하나 늘지만, 늘리지 않으면 위 둘 중 하나를 포기해야 한다.

## 6. 이번 스프린트에 적용하는 규칙

앞 두 스프린트에서 손해를 보고 세운 것들에 이번 것 하나를 더한다.

- **브랜치는 `feat/<스토리>`, 반영은 PR.** 통합 브랜치는 `develop`이다.
- **`npm run docs:check`가 CI 필수 단계다.** 이 문서의 숫자는 손으로 쓰지 않는다.
- **테스트는 병렬로 돌린다.** 직렬화는 Linux 락 결함을 가렸다.
- **검증 명령에 파이프를 붙이지 않는다.** 종료 코드가 바뀐다.
- **스토리를 열 때 인수조건이 이번 마일스톤에서 검증 가능한지 본다.**
- **미정을 적기 전에 PRD와 결정 기록을 먼저 뒤진다.** 이번에도 셋이 이미 답이 있었다.
- **UI 스토리는 브라우저 확인을 완료 조건에 포함한다.**
- **(신규) 거부 경로에 테스트가 없으면 그 인수조건은 닫지 않는다.** 이 스프린트 인수조건의
  절반이 401·403·409다. 성공 경로만 도는 테스트는 권한 스토리에서 아무것도 증명하지 않는다.
- **(신규) 동시성 인수조건은 진짜 동시 요청으로 검증한다.** r16a AC2는 2단계 구현을 명시적으로
  금지한다. 순차로 두 번 보내는 테스트는 그 금지를 확인하지 못한다.
