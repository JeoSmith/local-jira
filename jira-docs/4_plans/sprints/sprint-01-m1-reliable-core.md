### 타임박스를 두지 않는 이유와 그 대가

구현을 AI가 맡는 방식에서는 달력 기간이 진척을 대변하지 않는다. M0가 그 예다 — 문서·설계·구현·
CI·Linux 결함 수정까지 한 세션에 끝났고, 이를 "며칠짜리"로 환산하는 것은 의미가 없었다.

**대신 잃는 것도 분명하다.** 타임박스가 없으면 번다운도 벨로시티도 성립하지 않고, "언제 끝나는가"에
답할 수단이 사라진다. 그래서 다음 두 가지로 대체한다.

1. **Gate가 유일한 진도 단위다.** Wave의 모든 스토리가 끝나고 해당 Gate 시나리오가 통과해야 다음
   Wave로 넘어간다. "거의 다 됐다"는 상태를 인정하지 않는다.
2. **점수는 예측이 아니라 순서·위험 신호로만 쓴다.** 아래 추정은 무엇이 어렵고 무엇이 병목인지를
   말할 뿐, 완료 시점을 약속하지 않는다.

#### Linux 락 결함 — `--test-concurrency=1`이 가리고 있던 것

Gate 2 커밋의 CI는 ubuntu에서 실패했다(24건). 전부 같은 오류였다:

```
Detected unsettled top-level await at src/cli.ts:66   ← await runInitCommand(argv)
```

직렬 실행으로 바꾸자 초록이 됐지만, 그건 **고친 게 아니라 레이스에 들어가지 않게 한 것**이었다.
직렬화 비용은 스위트 런타임 35s → 131s였다.

진단은 ubuntu CI를 계측기로 써서 했다(macOS는 `O_EXLOCK` 경로라 이 코드를 아예 타지 않는다).

| 실험 | 결과 |
|---|---|
| 병렬 `init` 24개만 단독 실행 | 24/24 성공 — 락 단독으로는 재현 안 됨 |
| 스위트를 기본 동시성으로, 3회 | **8 · 7 · 12건 실패** — 재현율 100% |
| 위와 동일 + 수정 1건 | **0 · 0 · 0** |

원인은 `FlockHelperLock.release()`의 **핸들 비대칭**이다. 획득 시 `child`·`stdout`·`stderr`
셋을 모두 `unref()`하는데, 해제 시에는 `child`만 `ref()`한다. `close`는 자식 종료와 파이프
배수가 **모두** 끝나야 발생하므로, 그 사이 구간을 잡아두는 핸들이 없다. 이벤트 루프가 비면
Node는 종료하고, `release()`의 프로미스는 미해결로 남아 호출자의 `finally`가 끝나지 않는다.

이 경로가 유일한 용의자였던 이유는 **부트스트랩의 git 호출이 전부 `spawnSync`**라서다 —
Linux에서 `localjira init`의 비동기는 락 헬퍼 두 곳뿐이고, 미해결 await는 거기일 수밖에 없었다.

교훈 둘:

- **초록으로 만든 조치와 고친 조치는 다르다.** 직렬화는 증상을 없앴을 뿐 결함은 그대로
  남아 있었고, 그 사이 Wave 2 전체가 "CI 초록"이라는 잘못된 근거 위에 서 있었다.
- **파이프가 종료 코드를 삼킨다.** 진단 첫 판에 `node --test ... | tail -120`으로 돌려
  "현재 코드는 통과"라고 잘못 읽었다. 파이프를 걷어내자 바로 실패가 드러났다.

`npm test`는 병렬로 되돌렸다. **병렬 실행 자체가 이 결함의 재발 감시 장치**이기 때문이다.

넘기지 않으려면, 스토리를 열 때 그 인수조건이 **이번 마일스톤 안에서 검증 가능한지**를
분해 단계에서 한 번 더 본다.

감사 결과 뒤늦게 발견해 이번에 닫은 것 다섯:

- `acceptance` 필드가 생성 때만 되고 **수정이 불가**했다 (r01b) — `UPDATABLE` 누락
- `updated_at`·`last_actor_kind`가 생성 이후 **한 번도 갱신되지 않았다** (r01b)
- `rev` 카운터가 아예 없었다 (r10)
- 위 타임스탬프를 UTC로 찍으면 `+09:00`인 `created_at`보다 **문자열 정렬상 과거**가 되어,
  이벤트 로그에서 이미 한 번 고친 함정을 그대로 반복할 뻔했다
- r09의 동시 쓰기 테스트가 `.then()` 체이닝이라 **직렬화 큐를 한 번도 타지 않았다**.
  주석만 "overlap in flight"라고 적혀 있었다 — 통과하는 테스트가 아무것도 지키지 않던 경우

### Wave 3 — 대량 조정과 백로그 도메인

**r08c 완료.** 조정에서 드러난 것 하나가 설계를 바꿨다.

삭제 정책이 **세 경로에 각각 따로 있었다** — 증분 스캔은 행을 즉시 지우고, 전체 조정은
tombstone을 남기고, API 삭제(`syncPath`)는 또 즉시 지웠다. 그래서 "삭제된 이슈가 이력을
남기는가"가 **어느 트리거가 먼저 알아챘는지에 따라 달라졌다**. `retirePath` 하나로 합쳐
세 경로가 같은 답을 내도록 했다.

- 전체 조정은 `(mtime, size)` 지름길을 쓰지 않고 **모든 파일을 해시**한다. checkout 이후의
  stat 값은 증거가 못 된다 — 커밋 내용대로 쓰이므로 크기가 같은데 내용이 다를 수 있다.
- 사라진 파일은 **uid가 다른 경로에 살아 있으면 이동**, 아니면 tombstone(유예 60s).
  유예 안에 돌아오면 취소하고, 지나면 확정한다. 행은 지우지 않아 404가 마지막 경로를 답한다.
- 승격 트리거: `git_head_change`(HEAD·index·MERGE_HEAD) · `watcher_overflow`(창당 200건 초과,
  워처 오류·디렉터리 이벤트는 즉시) · `startup` · `manual`(`localjira index reconcile`).
- worktree가 제거됐는데 인덱스가 파일을 기억하고 있으면 **전량 삭제로 오인하지 않고**
  `E_WORKTREE_MISSING`으로 기동을 멈추고 `repair-worktree`를 안내한다.

성능은 여유가 크다 — **변경된 1,000파일 전체 조정 361ms**(N2 예산 15s).

**r02a 완료.** `parent`는 인덱싱만 되고 **검증도 API 설정 경로도 없었다** — 계층 규칙이
문서에만 있고 코드에 없던 상태였다. 타입별 허용 부모를 표로 두고(에픽=최상위, 작업형=에픽만,
subtask=작업형만, subtask는 부모가 될 수 없음) 생성·수정 양쪽에서 강제한다.

미정이던 `promote`+subtask 충돌은 **S1-D14로 확정**: 409 거부다. 부모 없는 subtask는 생성
경로가 400으로 막는 형태라, 승격으로 만들면 **API가 만들 수 없는 것을 인덱스가 갖게 된다**.

하위 이슈 목록은 본문이 아니라 `GET /issues/{key}/children`으로 뺐다. 본문은 파일의 표현이고
그 해시가 ETag이므로(ADR-003), 파생 목록을 넣으면 **남이 이 이슈로 재부모화할 때마다 내
validator가 움직여** 내가 하지도 않은 편집 때문에 412를 받게 된다. 상세 응답에는 개수만
`X-Child-Count`로 실어 화면이 목록을 요청할지 판단하게 했다.

**r02b 완료.** 스토리에 미정 2건이 달려 있었지만 **둘 다 S1-D4·S1-D5에서 이미 결정된
것**이었다 — 스토리를 열 때 결정 기록을 확인하지 않아 미정 표시가 남아 있었다. 참조로 바꿨다.

관계는 **선언한 쪽 파일에만** 저장한다(S1-D4). `A blocked_by B`를 걸면 A 파일만 바뀌고,
B에서 보이는 `blocks`는 인덱스 역참조로 계산한다. 양방향 저장이면 링크 하나에 두 파일을
고쳐야 해서 머지 충돌 면적이 두 배가 되고, 한쪽만 반영된 상태가 생긴다.

`claimable`은 미완료 `blocked_by`가 하나도 없을 때 참이며, `CANCELLED` 차단자는 해제로
본다(S1-D5) — 하지 않기로 한 일이 남의 진행을 영구히 막아서는 안 된다. 거부 사유(차단 중인
이슈 키)가 값과 함께 나가는데, 에이전트가 사람에게 왜 못 집는지 그대로 보고해야 하기 때문이다.

link_id는 `{kind}:{to_uid}`로 **쌍에서 파생**한다. 위치 인덱스로 잡으면 파일에 줄 하나만
끼어들어도 다른 링크를 가리키게 된다.

**r03 완료.** rank는 저장 형식이므로 예제 몇 개가 아니라 **property test**로 고정했다 —
의사난수 시드를 코드에 박아 실패가 정확히 재현되게 했다(의존성이 없으므로 생성기도 직접 썼다).

한 번의 이동은 파일 **1개**만 바꾼다(중간·최상단·최하단 모두 `git status`로 확인). 요청은
위치 인덱스가 아니라 **양쪽 이웃 uid**를 담는다 — 인덱스는 남이 재정렬하는 순간 다른 뜻이
되기 때문이다. 이웃이 더 이상 인접하지 않으면 409와 함께 **현재 순서**를 돌려준다.

같은 간격에 반복 삽입하면 **49회쯤에 32자 상한**에 걸린다. AC가 요구한 1,000회는 재균형
없이는 불가능하며, 그게 AC의 의도다. 소진 시 앞뒤 각 64개를 균등 재배치한다.

생성 시 `backlog_rank`를 부여하도록 했다. 비워 두면 SQLite가 NULL을 앞에 정렬해서,
**첫 재정렬이 카드를 반대 방향으로 보내는 것처럼 보인다**.

5,000건 백로그 첫 페이지 조회 **p95 3ms**(N1 예산 1s).

**남은 격차 하나**: 재균형이 파일 간 원자적이지 않다. 대상 존재를 먼저 전량 확인하지만 쓰기는
순차라, 중간에 죽으면 일부만 재배치된 채 남는다. 순서는 모든 클론에서 동일하고 다음 재균형이
정리하지만, ADR-005가 요구한 단일 다중 파일 WriteTxn은 outbox가 여러 경로를 담아야 해서
r09의 검증된 복구 기계를 건드린다. 이번 마일스톤 밖으로 두고 스토리에 명시했다.

## 완료 절단선 (적용 완료)

절단은 **이미 반영됐다.** Wave 1~4의 16건이 Sprint 01이고, Wave 5의 4건은 Sprint 02로 넘긴다.

- **Sprint 01 (16건 76점)**: 안전한 생성·수정·외부 조정·격리·필터까지. 인덱스를 지워도 파일에서
  동일하게 복구되고, 크래시·git 대량 변경 뒤에도 수렴하는 코어가 선다.
- **Sprint 02 이월 (4건 14점)**: `r11b` 오류 배너 · `r21` 수동 재인덱스 · `r26` 재키잉 ·

**Wave 중간에서 더 자르지 않는다.** `r08c` 없이 `r11a`를, `r04a` 없이 `r04b`를 완료로 잡으면
스토리의 통합 인수조건을 검증할 수 없다. 범위를 더 줄여야 하면 Wave 4를 통째로 넘기는 식으로
Gate 단위로 자른다.
